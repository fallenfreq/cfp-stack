# Database: how we use Drizzle

How the API talks to D1, and the plan that gets the code there. The code this plan touches
should end up as the example for anything new.

## How we use it

- **One database type, no table list.** `drizzle(env.DB)`, and everything that takes the
  database (the tRPC context, routes, domain, auth) names it `Db` (`api/src/db.ts`), so a change
  to it is made in one place. Queries are built with the query builder (`db.select().from(table)`, `insert`, `update`, `delete`), which is typed from the
  table each call names: the columns picked, the conditions, the values written and what
  `.returning()` gives back. Nothing is registered.
- **Relational queries (`db.query`, `with:`) only where reading nested rows pays off**, and then
  only those tables and their relations (`defineRelations`, Drizzle 1.0) are registered. Typing
  `db` with every table stalled the type checker on Drizzle 0.30 (tried 2026-10-04: no result in
  five minutes).
- **Row types come from the tables**: `typeof table.$inferSelect` / `$inferInsert`, never
  written by hand.
- **No `sql` templates.** `sql<T>` asserts a type nothing checks. Use the builder's operators
  and do the rest in code (for example, group joined rows in TypeScript rather than with
  `GROUP_CONCAT`). SQLite's `LIKE` already ignores case for ASCII, so there's no `lower()` or
  `ilike` (which SQLite doesn't have).
- **Writes that must happen together go in one `db.batch([…])`.** D1 runs a batch as one
  transaction: if a statement fails, none of them stays. D1 has no transaction you can hold
  open, so `db.transaction()` isn't used. When a later write needs an id an earlier insert makes,
  the id is chosen in code beforehand, or the write is arranged so it doesn't need it.
- **Migrations** are generated by drizzle-kit from `api/src/schemas` (built to `dist`) and
  applied by wrangler (`pnpm migrate:push:local:api`, then `pnpm migrate:push:api` for live).

## Plan

Each step: show the plan → build → check (type checks, tests, the dev server) → agent review
→ verify its findings → the owner approves the commit → commit only that step's files →
update Progress → compact. Another session shares `main`: stage only this work's files and
hunks. Live changes (D1 migrations, Cloudflare settings) need manual mode and the owner's go-ahead
for each; pushing is the owner's call.

1. **Old reference code out, one `Db` type** (code only).
    - The starter's `user` router: removed; `docs/auth.md` updated.
    - The table list: `drizzle(env.DB)` in `functions_src/trpc/[[trpc]].ts`. `Db`
      (`DrizzleD1Database`, nothing registered) moves from `domain/types.ts` to its own
      `api/src/db.ts`, so auth can use it without depending on the domain; the context, the
      markers router's helper and `auth/sessions.ts` take it too. The `schemas` const and its
      comment are gone, and so is `schemas/index.ts`, the object of every table nothing used.
    - The SMTP settings: nothing sends email yet, but every tRPC and stylesheet request required
      them. Out of `config/envs.ts`; they stay in `api/wrangler.toml` and
      `api/.dev.vars.example`, marked unused, for when the app sends email (the owner's choice).
2. **The starter's tables out** (schema, then live).
    - `posts`, `categories`, `categories_posts`, `profiles` and every `relations(…)` leave
      `schemas/user.ts`; `users` stays (the seed's brand user owns the seeded themes).
    - `pnpm build:api && pnpm migrate:api` makes the migration (the current drizzle-kit); apply
      locally, check the app and seed.
    - Live: count the four tables' rows first (read-only); export any the owner wants kept. Push
      the code, then apply the migration (manual mode).
3. **Drizzle 1.0**: `drizzle-orm` and `drizzle-kit` 0.30 / 0.20 → `1.0.0-rc.4` (the owner's
   choice: the release candidate, Jun 2026, over 0.45.3 stable).
    - First check how drizzle-kit 1.0 lays out `migrations/`: wrangler applies the `.sql` files
      it finds there by name, and `d1_migrations` on live records `0000_…` and `0001_…`. If
      1.0 writes a folder per migration, settle how wrangler gets the files before anything
      else.
    - Read the upgrade guide and release notes (relations v2, `drizzle()` options, removed APIs);
      `drizzle.config.ts` takes `dialect: 'sqlite'` (no driver is needed to generate);
      `generate:sqlite` becomes `generate`; `drizzle-kit up` upgrades `migrations/meta`.
    - Proof: `pnpm migrate:api` then makes no new migration; type checks, tests and the app pass.
    - Locally, `pnpm install` will offer to rebuild `node_modules`; CI and Cloudflare install
      fresh.
4. **No `sql` templates** (`routes/markers/router.ts`: `lower()`, `ilike`, `GROUP_CONCAT`; the
   map stays, so they're rewritten, not removed). `ilike` is also a bug: Drizzle writes
   `title ilike '%…%'`, which SQLite refuses, so every marker search by text that isn't exact
   fails with a 500.
5. **Batch what must happen together.** Found so far:
    - `pages.update`: the page, then its tags deleted, then inserted (a failed insert leaves the
      page with no tags).
    - `createClassRule` (the rule, its classes, `touchTheme`), `deleteClassRule`, `setToken` and
      `unsetToken` (each write and `touchTheme`).
    - The markers router's `insert` and `update`.
    - `auth/sessions.ts`: check each; its housekeeping deletes can stay separate.
6. **Input validators from the tables** (`drizzle-orm/zod`, built into 1.0; agreed 2026-10-05).
   Routes that write a table's rows (pages, tags, markers) take their input from the table, so a
   column change breaks the validator at compile time; inputs that aren't rows (the account's,
   from Zitadel) stay written by hand. zod 3.23 → 4 (1.0 accepts ≥ 3.25 or 4); only the API
   uses zod.
7. **Write it down**: this page's "How we use it" stays current; `CLAUDE.md` points to it
   (with the owner's go-ahead).
