# Database: how we use Drizzle

How the API talks to D1. The code that follows it is the example for anything new.

## How we use it

- **One database type, no table list.** `drizzle(env.DB)`, and everything that takes the
  database (the tRPC context, routes, domain, auth) names it `Db` (`api/src/db.ts`), so a change
  to it is made in one place. Queries are built with the query builder
  (`db.select().from(table)`, `insert`, `update`, `delete`), which is typed from the table each
  call names: the columns picked, the conditions, the values written and what `.returning()`
  gives back. Nothing is registered.
- **Relational queries (`db.query`, `with:`) only where reading nested rows pays off**, and then
  only those tables and their relations (`defineRelations`, Drizzle 1.0) are registered. Typing
  `db` with every table stalled the type checker on Drizzle 0.30 (tried 2026-10-04: no result in
  five minutes).
- **People live in Zitadel.** A row that needs a person stores Zitadel's user id, as
  `sessions.subject` does; there's no users table of our own.
- **Row types come from the tables**: `typeof table.$inferSelect` / `$inferInsert`, never
  written by hand.
- **No `sql` templates.** `sql<T>` asserts a type nothing checks. Use the builder's operators
  and do the rest in code (for example, group joined rows in TypeScript rather than with
  `GROUP_CONCAT`). SQLite's `LIKE` already ignores case for ASCII, so there's no `lower()` or
  `ilike` (which SQLite doesn't have); a `%` or `_` in the text searched for matches any
  characters.
- **Writes that must happen together go in one `db.batch([…])`**, or `writeTogether` (`db.ts`)
  for a list built from what was sent, which may be empty. D1 runs a batch as one transaction: if
  a statement fails, none of them stays. D1 has no transaction you can hold open, so
  `db.transaction()` isn't used. Checks that read come first, then the batch. When a later write
  needs an id an earlier insert makes, the id is chosen in code beforehand (a theme's), or the
  write reads it in the batch: pairs are inserted from a select (a marker and the tags named, so
  a tag inserted earlier in the batch is paired too), and `newestId` gives the row the batch just
  inserted.
- **Inputs come from the tables.** A route that writes a table's rows builds its validator with
  `createSelectSchema(table, { … })` (`drizzle-orm/zod`): the columns give the types and lengths
  (SQLite doesn't hold a text column to its length, so the validator does), the refinements add
  what the app asks (a name trimmed and not empty, `nameRule`; `slugRule`; an http(s) address),
  and each input picks the columns it takes. A column renamed or retyped breaks the input at
  compile time. Reads that name a row by slug or id take the same fields; inputs that aren't rows
  (the account's) are written by hand. A list bound to one query has a limit a request, as D1
  takes at most 100 values a query. Changing a row that isn't there answers 404: the write's
  `.returning()` says so, or, before a batch, `mustExist` (`lib`) checks first. Deleting one that
  isn't there answers success.
- **Migrations** are generated by drizzle-kit from `api/src/schemas` (it reads the TypeScript),
  one folder each in `api/migrations` (`migration.sql`, `snapshot.json`), and applied by
  wrangler, which finds them through `migrations_pattern` (`pnpm migrate:push:local:api`, then
  `pnpm migrate:push:api` for live, as "Applying a migration on live" says). Wrangler records
  each one applied in `d1_migrations` under its path, so moving or renaming a migration's folder
  means renaming its row, locally and on live. A migration is committed with the schema change
  that made it. Read each one before applying it:
    - Dropping a column that has a foreign key, or changing a table's keys or constraints,
      rebuilds the table, and on D1 dropping the old one deletes every row that cascades from
      it: D1 keeps foreign keys on inside a migration, so the `PRAGMA foreign_keys=OFF`
      drizzle-kit writes there does nothing (drizzle bug #5782, open). Rebuilding a table
      nothing points at is safe, as in `…_keys_and_indexes`; otherwise the migration keeps
      those rows aside and puts them back, as `…_plain_wild_pack` does. Dropped tables go
      children first.
    - drizzle-kit 1.0 writes a single-column primary key without `NOT NULL`, even when the
      schema says it, and SQLite then accepts NULL in a key that isn't an integer. A migration
      that creates or rebuilds a table with a text key gets `NOT NULL` added by hand.
    - A migration's comments have no `;`. Live D1 splits the SQL at each `;` without seeing
      comments, so a `;` in one leaves a piece with no statement, and the migration fails
      ("SQL code did not contain a statement"). Locally wrangler splits it itself, so only live
      would show it: `api/test/migrations.test.mjs` checks for it.
- **A unique value is a `uniqueIndex()`**, not `.unique()`: drizzle-kit 1.0 writes `.unique()`
  into the table, which SQLite can only add or drop by rebuilding it; an index comes and goes on
  its own. A row that may be there already is inserted with `onConflictDoNothing()` and then
  read, never looked for first: between the look and the insert, another request can add it.
  A slug that's taken is another row's: one made from a name moves aside (`-2` to `-10`, within
  the column's length, then 409; `insertWithUniqueSlug`), and one the admin chose answers 409
  (`conflictIfSlugTaken`). Both are told the slug column, and `isUniqueViolation` checks the
  repeat is in it.
- **Every foreign key's column leads an index** (or the primary key). Deleting a row finds the
  rows pointing at it through that index; without one, SQLite reads the whole table for each row
  deleted (deleting the design read 326,276 rows before `…_keys_and_indexes`, 2 after).
- **Database errors are read through `api/src/db.ts`.** Drizzle wraps a failed query in an error
  whose message is the query with its values: `isUniqueViolation` checks what the database said,
  and logs print `databaseError(error)`, never the query.

## Applying a migration on live

1. **Read-only checks**, from `api/`:
    - `pnpm exec wrangler d1 migrations list somefreq-db --remote` shows only the migrations
      meant to run.
    - In `sqlite_master`, nothing else points at a table the migration rebuilds, or its rows go
      with the old table ("Migrations" above), and no name it creates (an index, a table) is
      taken.
    - The foreign-key check (`PRAGMA foreign_key_check`, through
      `pnpm exec wrangler d1 execute somefreq-db --remote --command`) is clean: a rebuild with a
      key that points at nothing stops, and changes nothing.
    - The rows of each table it touches are counted, and any the owner wants kept are exported.
      Where it changes or merges rows, a query that only reads shows what it will do.
2. **Note the Time Travel bookmark** (`pnpm exec wrangler d1 time-travel info somefreq-db`), so the
   database can be put back to it.
3. **Order it with the push.** Production and every older deployment share the database
   (`docs/hosting.md`, "D1"). A migration that takes away what the running code reads waits
   until the push that stops reading it is live; one that the new code relies on goes first.
4. **Apply it:** `pnpm migrate:push:api`, from the root.
5. **Check:** the rows it touched, counted against before; the foreign-key check; and, when it
   touched the design's tables, the stylesheet (`/styles/sf-system`), byte for byte as before.

## Decisions

- **The map demo stays** (2026-10-05), so its router keeps to the same standard.
- **Live's map data may go** (2026-10-06). The owner doesn't need the map demo's rows
  (`map_markers`, `tags`, `marker_tags`) kept, so a migration or clean-up of those tables needn't
  go out of its way to keep them; it still says what it deletes before it runs. This doesn't
  reach the design's tables, pages or sessions.
- **Drizzle 1.0's release candidate** (2026-10-05): `drizzle-orm` and `drizzle-kit`
  `1.0.0-rc.4`, the owner's choice over 0.45.3 stable, pinned. So is wrangler (4.147.0, an api
  devDependency, not whatever `npx` finds).
- **Live's drift is left as it is** (2026-10-05). Two tables on live differ from what
  `0000` makes. `site_pages` and `collection_entries` have their columns in another order
  (harmless: Drizzle names every column). `site_pages.content_json` defaults to `'{}'`, not
  the empty document, and nothing relies on it (`pages.create` always writes it). From
  2024-09 to 2026-10-01 migration files weren't in git, so each setup made its own set from
  `0000` and live applied three of them: later columns came as `ADD COLUMN`, which appends
  them, and the default change (2026-06-15) needed a rebuild drizzle-kit 0.20 doesn't write.
  Live was brought in line by adding the missing tables and marking `0000` applied, so the
  older tables kept their shapes. A future rebuild of either table puts it right.

## Known issues

- **Themes, for when there's a theme editor.** A theme's `updated_at` is in whole seconds, so a
  token changed within the same second as the last change leaves the stylesheet's cache as it
  was. The duplicate-rule check reads before it inserts, so two requests at once could both add
  the same rule. A vocabulary entry removed between a new rule's checks and its batch leaves the
  rule without that class.
- **Slugs made from names.** Only a–z and 0–9 are kept, so `Café` makes `caf`, and a name with
  neither (`Ελλάδα`, `Москва`, `日本`) makes `untitled`, whatever it says. A slug moves aside
  only as far as `-10`, so an 11th page or collection whose name makes the same slug can't be
  made (409): an 11th named `Test`, or an 11th named in another script. A slug holds only a–z,
  0–9 and hyphens (`slugRule`), so a fix changes how a slug is made or what it may hold.
- **The map.** Any signed-in user can change or delete any marker or tag (`api/src/routes/markers`):
  the map is a demo and the owner has the only account. A new marker's pin shows its title as
  typed, the server's trimmed. Live keeps 13 tag names from before tags were normalized (`Food`
  beside `food`), on no marker.
