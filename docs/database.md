# Database: how we use Drizzle

How the API talks to D1, and the plan that gets the code there. The code this plan touches
should end up as the example for anything new.

## How we use it

- **One database type, no table list.** `drizzle(env.DB)`, and everything that takes the
  database (the tRPC context, routes, domain, auth) names it `Db` (`api/src/db.ts`), so a change
  to it is made in one place. Queries are built with the query builder
  (`db.select().from(table)`, `insert`, `update`, `delete`), which is typed from the table each
  call names: the columns picked, the conditions, the values written and what `.returning()`
  gives back. Nothing is registered.
- **Relational queries (`db.query`, `with:`) only where reading nested rows pays off**, and then
  only those tables and their relations (`defineRelations`, Drizzle 1.0) are registered. Typing
  `db` with every table stalled the type checker on Drizzle 0.30 (tried 2026-10-04: no result in
  five minutes).
- **People live in Zitadel.** A row that needs a person stores Zitadel's user id, as
  `sessions.subject` does; there's no users table of our own.
- **Row types come from the tables**: `typeof table.$inferSelect` / `$inferInsert`, never
  written by hand.
- **No `sql` templates.** `sql<T>` asserts a type nothing checks. Use the builder's operators
  and do the rest in code (for example, group joined rows in TypeScript rather than with
  `GROUP_CONCAT`). SQLite's `LIKE` already ignores case for ASCII, so there's no `lower()` or
  `ilike` (which SQLite doesn't have); a `%` or `_` in the text searched for matches any
  characters.
- **Writes that must happen together go in one `db.batch([…])`.** D1 runs a batch as one
  transaction: if a statement fails, none of them stays. D1 has no transaction you can hold
  open, so `db.transaction()` isn't used. When a later write needs an id an earlier insert makes,
  the id is chosen in code beforehand, or the write is arranged so it doesn't need it.
- **Migrations** are generated by drizzle-kit from `api/src/schemas` (it reads the TypeScript),
  one folder each in `api/migrations` (`migration.sql`, `snapshot.json`), and applied by
  wrangler, which finds them through `migrations_pattern` (`pnpm migrate:push:local:api`, then
  `pnpm migrate:push:api` for live). Read each one before applying it:
    - Dropping a column that has a foreign key, or changing a table's keys or constraints,
      rebuilds the table, and on D1 dropping the old one deletes every row that cascades from
      it: D1 keeps foreign keys on inside a migration, so the `PRAGMA foreign_keys=OFF`
      drizzle-kit writes there does nothing (drizzle bug #5782, open). Rebuilding a table
      nothing points at is safe, as in `…_keys_and_indexes`; otherwise the migration keeps
      those rows aside and puts them back, as `…_plain_wild_pack` does. Dropped tables go
      children first.
    - drizzle-kit 1.0 writes a single-column primary key without `NOT NULL`, even when the
      schema says it, and SQLite then accepts NULL in a key that isn't an integer. A migration
      that creates or rebuilds a table with a text key gets `NOT NULL` added by hand.
    - A migration's comments have no `;`. Live D1 splits the SQL at each `;` without seeing
      comments, so a `;` in one leaves a piece with no statement, and the migration fails
      ("SQL code did not contain a statement"). Locally wrangler splits it itself, so only live
      shows this.
- **A unique value is a `uniqueIndex()`**, not `.unique()`: drizzle-kit 1.0 writes `.unique()`
  into the table, which SQLite can only add or drop by rebuilding it; an index comes and goes on
  its own. A row that may be there already is inserted with `onConflictDoNothing()` and then
  read, never looked for first: between the look and the insert, another request can add it.
- **Every foreign key's column leads an index** (or the primary key). Deleting a row finds the
  rows pointing at it through that index; without one, SQLite reads the whole table for each row
  deleted (deleting the design read 326,276 rows before `…_keys_and_indexes`, 2 after).
- **Database errors are read through `api/src/db.ts`.** Drizzle wraps a failed query in an error
  whose message is the query with its values: `isUniqueViolation` checks what the database said,
  and logs print `databaseError(error)`, never the query.

## Plan

Each step: show the plan → build → check (type checks, tests, the dev server) → agent review
→ verify its findings → the owner approves the commit → commit only that step's files →
update Progress → compact. Another session shares `main`: stage only this work's files and
hunks. Live changes (D1 migrations, Cloudflare settings) need manual mode and the owner's go-ahead
for each; pushing is the owner's call.

1. **Old reference code out, one `Db` type** (code only).
    - The starter's `user` router: removed; `docs/auth.md` updated.
    - The table list: `drizzle(env.DB)` in `functions_src/trpc/[[trpc]].ts`. `Db`
      (`DrizzleD1Database`, nothing registered) moves from `domain/types.ts` to its own
      `api/src/db.ts`, so auth can use it without depending on the domain; the context, the
      markers router's helper and `auth/sessions.ts` take it too. The `schemas` const and its
      comment are gone, and so is `schemas/index.ts`, the object of every table nothing used.
    - The SMTP settings: nothing sends email yet, but every tRPC and stylesheet request required
      them. Out of `config/envs.ts`; they stay in `api/wrangler.toml` and
      `api/.dev.vars.example`, marked unused, for when the app sends email (the owner's choice).
2. **The starter's tables out, `users` with them** (schema, then live).
    - `schemas/user.ts` is gone: `posts`, `categories`, `categories_posts`, `profiles`, their
      relations and `users`. So is what hung on `users`: `themes.created_by` (only the seed
      wrote it, nothing read it), `user_theme_aliases` and its three functions (nothing called
      them) and the seed's brand user. Something that needs an owner later stores Zitadel's
      user id.
    - `migrations/…_plain_wild_pack` (then `0002_plain_wild_pack.sql`): generated, then
      finished by hand ("How we use it", migrations): `themes` is rebuilt without
      `created_by`, keeping its tokens, rules and rule classes.
    - Live, in manual mode. First the read-only checks: `wrangler d1 migrations list --remote`
      shows only `0002` waiting; live's tables (`sqlite_master`) are the ones `0000` and `0001`
      make, with nothing else pointing at `themes`, `class_rules` or a dropped table (live's
      tables came from older migrations and a one-off file); and the rows in the starter
      tables, `users` and `user_theme_aliases` are counted, any the owner wants kept exported.
      Note D1's Time Travel bookmark (`wrangler d1 time-travel info`) so the database can be
      put back. Then push, and apply the migration once that push's deployment is live: until
      then live runs code that reads `themes.created_by`. Older deployments share the database,
      so their links stop working then.
3. **Drizzle 1.0**: `drizzle-orm` and `drizzle-kit` 0.30 / 0.20 → `1.0.0-rc.4` (the owner's
   choice: the release candidate, Jun 2026, over 0.45.3 stable), pinned; so is wrangler
   (4.147.0, an api devDependency rather than whatever `npx` finds).
    - drizzle-kit 1.0 writes each migration as a folder; `drizzle-kit up` moved ours, their SQL
      unchanged. Wrangler (4.98 and later) finds them through `migrations_pattern` and records
      each under its path, so the three applied migrations' rows in `d1_migrations` are renamed
      to the new paths, locally and on live.
    - 1.0 read our schema differently and would have rebuilt five tables. `.unique()` became
      `uniqueIndex()`, which is what the database has. 0.20 had sorted the columns of the
      composite keys of `theme_tokens` and `class_rule_classes`, so a lookup by theme or by rule
      read the whole table; `…_keys_and_indexes` rebuilds both (nothing points at them) with
      the schema's order, and indexes `class_rules.theme_id` and
      `class_rule_classes.class_name`.
    - 1.0 wraps a failed query in `DrizzleQueryError`, so the checks for a taken slug and a
      taken theme id stopped matching; both use `isUniqueViolation` (`db.ts`), and the logs
      print `databaseError(error)` instead of the query's values.
    - 0.30's types brought Cloudflare's Workers types into the client's type check;
      `routes/appRouter.ts` now names them.
    - `drizzle.config.ts`: `dialect: 'sqlite'`, reading `src/schemas` (no build first);
      `generate`; table extras as arrays; the in-memory D1 reads the folders; pnpm runs
      workerd's install script, as it does esbuild's.
    - Live, in manual mode. First the read-only check: no other table in `sqlite_master`
      mentions `theme_tokens` or `class_rule_classes`, so nothing cascades from the rebuild,
      and neither index name is taken. Note the Time Travel bookmark; rename the three rows;
      `wrangler d1 migrations list --remote` then shows only `…_keys_and_indexes`; apply it
      (before or after the push: the code doesn't depend on keys or indexes); check the counts
      and the stylesheet.
4. **No `sql` templates** (`routes/markers/router.ts`: `lower()`, `ilike`, `GROUP_CONCAT`; the
   map stays, so they're rewritten, not removed).
    - `ilike` was also a bug: Drizzle writes `title ilike '%…%'`, which SQLite refuses, so every
      marker search by text that wasn't exact answered 500. A search now matches with `like`,
      an exact one with `eq`, so there a title's case counts (tags are stored lowercase).
    - `GROUP_CONCAT` joined the tags of the rows the search kept, so a marker found by one tag
      came back with that tag only. The search now picks markers (by title, or through a
      subquery those carrying a matching tag) and each comes back with all its tags, the rows
      grouped in TypeScript.
    - `marker_tags` had no key and no index: a marker could carry a tag twice, and deleting a
      marker or a tag read the whole table. It takes `site_page_tags`' shape; `…_marker_tag_keys`
      rebuilds it (nothing points at it). A tag's name is unique (`tags_name_unique`), so two
      requests adding the same new tag add it once. Adding a tag a marker carries already adds
      nothing, and the answer names only the tags added.
    - The old code looked a tag up before adding it, so a name could be stored twice (live had
      `test` twice). The migration merges them: a name keeps its first tag, the pairs move to
      it, once each, and the other copies go.
    - Live, in manual mode. First the read-only check: no row of `marker_tags` pointing at
      nothing (the foreign-key check), which stops the migration, which then changes nothing.
      Nothing else in `sqlite_master` mentions `marker_tags`, and neither index name is taken.
      Note the Time Travel bookmark and apply the migration, then push: the new code relies on
      the unique name (without it, adding a tag that exists adds it again). Until then the old
      code runs as before, except that adding a tag twice answers 500 rather than storing it
      twice.
5. **Batch what must happen together.** Found so far:
    - `pages.update`: the page, then its tags deleted, then inserted (a failed insert leaves the
      page with no tags).
    - `createClassRule` (the rule, its classes, `touchTheme`), `deleteClassRule`, `setToken` and
      `unsetToken` (each write and `touchTheme`).
    - The markers router's `insert` and `update`; `update`'s `filterUndefined` (and its `any`)
      goes, as `.set()` leaves out what's undefined itself.
    - `auth/sessions.ts`: check each; its housekeeping deletes can stay separate.
    - The in-memory D1 (`client/e2e/d1Memory.mjs`) runs a batch's statements one by one, so in
      memory a failed statement leaves the earlier ones in place; it runs them as one
      transaction, as D1 does, before anything tested there relies on a batch.
6. **Input validators from the tables** (`drizzle-orm/zod`, built into 1.0; agreed 2026-10-05).
   Routes that write a table's rows (pages, tags, markers) take their input from the table, so a
   column change breaks the validator at compile time; inputs that aren't rows (the account's,
   from Zitadel) stay written by hand. zod 3.23 → 4 (1.0 accepts ≥ 3.25 or 4); only the API
   uses zod. Found in the markers router: `normalizeTags` drops empty names before trimming, so
   a tag of spaces is saved as `''`, and a tag that isn't there answers 500 rather than 404
   (`NotFoundError`). On live (2026-10-06), 34 of the 40 tags are on no marker, and 13 names
   date from before `normalizeTag` (`Food` beside `food`), all on no marker.
7. **Write it down**: this page's "How we use it" stays current; `CLAUDE.md` points to it
   (with the owner's go-ahead).

### Decisions

- **The map demo stays** (2026-10-05), so its router is brought up to the same standard.
- **Live's drift is left as it is** (2026-10-05). Two tables on live differ from what
  `0000` makes. `site_pages` and `collection_entries` have their columns in another order
  (harmless: Drizzle names every column). `site_pages.content_json` defaults to `'{}'`, not
  the empty document, and nothing relies on it (`pages.create` always writes it). From
  2024-09 to 2026-10-01 migration files weren't in git, so each setup made its own set from
  `0000` and live applied three of them: later columns came as `ADD COLUMN`, which appends
  them, and the default change (2026-06-15) needed a rebuild drizzle-kit 0.20 doesn't write.
  Live was brought in line by adding the missing tables and marking `0000` applied, so the
  older tables kept their shapes. A future rebuild of either table puts it right.
